# Evaluation protocol

## Purpose

Make every metric traceable and reproducible, and keep a clear distinction between historical internal baselines, development sets and future hidden test sets. M00 does not rerun historical E2E runs that need network access, Ollama or the large PBF; it only freezes existing machine-readable results and verifies the offline regression.

## Test layers and markers

| Layer | Runs by default | Allowed dependencies |
|---|---|---|
| `offline` | yes | Committed code and small fixtures; network access and implicit downloads are forbidden. |
| `model` | no | An explicitly specified local model/Ollama. |
| `network` | no | Nominatim, download sites or other external services. |
| `large_data` | no | The uncommitted large PBF or future real data. |
| `e2e` | no, unless explicitly selected | May combine model/network/large_data; data and configuration must be recorded. |

The standard offline command is `scripts\test_offline.cmd`, which runs compilation, `unittest` and the reproducibility audit in order.

## Data splits and leakage prevention

- `benchmarks/data/dev/` holds visible development samples; they may be used for debugging, but results must be labelled dev.
- `benchmarks/data/test/` stores only public schemas/descriptions; future hidden queries must never enter prompt examples, knowledge aliases or development fixtures.
- Evaluation build scripts must record the random seed, data version, code commit, model, prompt and configuration hash.
- Historical results are never overwritten in place; M11 uses run directories with a timestamp and configuration hash.
- An LLM judge may only be used for explanation quality that cannot be scored deterministically, and is reported separately from deterministic spatial metrics.

### M11a calibration entry point

- Command: `python -m benchmarks.run_m11a_benchmark`.
- Inputs: `m11a_tasks_v1.jsonl` and `m11a_calibration_predictions_v1.jsonl`, both public synthetic dev data written by the project author.
- Outputs: `benchmarks/results/runs/<UTC timestamp>-<config hash>/report.json` and `report.md`; an existing directory is never overwritten.
- Reports must keep `framework_calibration=true` and state clearly that numbers such as 15/24 are not agent, validator, hidden-set or production performance.
- The M11a bbox IoU is a lightweight contract calibration; real geometric topology/approximate equivalence and the formal dataset are left to M11b.

## Change gates

- Every module runs at least its relevant tests and the full offline regression.
- Metric regressions must be explained in the handoff; the number of new features must never hide a regression.
- Tests that need network/models/large data but were not run must be recorded with the reason and never reported as passing.

## M11b deterministic spatial scoring protocol (2026-10-07)

- `M11B_EVALUATION_FREEZE.md` was frozen before development; the 160 public dev tasks were published exclusively in a new version, and then 40 separate private test tasks were frozen in a supplementary step, 200 in total. The 24 M11a calibration tasks are kept but not counted in these 200.
- The 144 public supported tasks cover six operation types, and their reference results come from actual execution of the existing M04 allow-list; 8 rank tasks must be classified `unsupported_rank`, and 8 missing-place tasks must be clarified. The 40 private tasks use separate synthetic coordinates/Feature IDs and are git-ignored; the public receipt stores only hashes/versions/counts. Public and private queries do not overlap, and private content never enters prompt examples, knowledge aliases or development fixtures.
- Required fields are exact, semantic steps are an ordered subsequence, and the M04 tool sequence is exact in full order; Feature ID P/R/F1 is 1 when both sides are empty and 0 when only one is. Counts are exact; areas/distances use a tolerance of max(1e-6, |reference|×1e-6); real polygon IoU threshold 0.999999; points/lines must be topologically equal or have Hausdorff ≤ 1e-6; CRS must be explicitly equivalent. Invalid geometry, missing fields, `partial` passed off as `success` and mismatched reasons all fail. Rank has no supported reference, so no ranking success rate is reported; nDCG is reserved for future applicable supported ranking tasks.
- `scripts.audit_m11b_reproducibility` rebuilds the public/private references, checks hashes and query isolation, and self-checks with reference predictions. The reference self-check is not agent/validator performance. `benchmarks.run_m11b_scoring` accepts external v2 predictions and produces exclusive JSON/Markdown; private test outputs only aggregates, and the formal test must run after M11c locks its configuration. The three M11c baselines, three runs per configuration and the final comparison report are not implemented in M11b.

M11b's `m11b_tool_traces_v1.jsonl` stores, at the level of real M04 calls, tool versions, input/parameter/output hashes and row counts; byte-level rebuilds are checked by `scripts.audit_m11b_reproducibility`. It contains no random DatasetRef IDs, run timestamps or private questions. Private queries are scanned against the public benchmark, agent source code, knowledge files and development fixtures, and the expected number of exact leaks is 0.

Cross-platform note (2026-11-21): the frozen M11b release was built on Windows (shapely 2.1.2/GEOS 3.13.1). On Linux CI, GEOS buffer arithmetic produced a coordinate that differs in its last digit, so byte identity of the rebuild is required only on the reference platform. Elsewhere the offline tests require the rebuilt tasks, manifest and tool traces to match the frozen release structurally, with every float equal within a relative 1e-9 and only geometry-derived hashes excluded. The audit scripts remain byte-exact. The M06b fixture builder now pins the ZIP "version made by" system to 0, so that fixture rebuilds byte for byte on every OS.
