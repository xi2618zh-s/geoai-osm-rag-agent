This translation is provided for readers and is not part of the frozen evidence; if the two differ, the original applies.

- Date: 2026-10-07; version: m11b-public-dev-v1; build seed: 1107.
- Scope: 160 public synthetic dev tasks. M11a's 24 calibration tasks and faulty predictions stay where they are; M11b starts a new formal data version, and the v1.0 contract stays compatible. M11b does not run the three M11c system baselines.
- Distribution: 24 tasks each for search, within_distance, nearest, within, spatial_join and aggregate_by_region, 144 executable tasks in total; 8 explicitly unsupported rank tasks; 8 clarification tasks with a missing place. References are generated from real M04 tool outputs on the public m04b-v1 fixture; builder outputs are never passed off as dynamic-agent results.
- Split: this version publishes only dev. The test directory contains only the protocol, without queries, answers, seeds or templates from which they could be reverse-engineered. A hidden test must be kept separately, with an independent source and an independent ID namespace, and generated and evaluated by a non-developer custodian after the system/prompt are formally locked. Hidden content must never enter prompt examples, M03 knowledge aliases, development fixtures, code or logs. Before publication, public queries are scanned for normalized duplicates and for duplicates across M11a/M03 queries; no hidden score is claimed without actual hidden data.
- Source/licence: synthetic tasks and reference answers by the project author, CC0-1.0; geographic inputs from `data/fixtures/tools/m04b/v1`, also synthetic by the project author, CC0-1.0. No real personal data, external city coverage or network data. The build verifies every input hash in the fixture manifest and writes the build seed, version, command, tool allow-list, file SHA-256 and dependency versions into the output manifest. Output files are published exclusively.

## Scoring contract v2.0

- v2.0 tasks/predictions are independent of M11a v1.0, which keeps its loading and scoring behaviour; unknown fields are rejected. The success, clarification, error and partial statuses are distinct; for non-success, the reason code must match exactly. `partial` cannot pass for `success`, even when some features or numbers are correct.
- Required fields are compared exactly by key and value, with missing and wrong values recorded separately. Required semantic steps are scored as an ordered subsequence; real M04 tool names are scored exactly as the complete call sequence, and extra, missing or reordered calls all fail. Scoring only reads the structured trace in the prediction and never executes tools or paths proposed by it. Tool names must belong to the M04 allow-list.
- Feature IDs are a set: when both sides are empty, P/R/F1 = 1; when only one side is empty, all are 0; otherwise TP/predicted, TP/reference and their harmonic mean. Duplicate IDs are rejected. Missing fields, geometry or numbers in a success result each score 0 and are never ignored silently. An overall pass requires every applicable component to pass; partial scores are diagnostic only.
- Numbers: |actual − reference| ≤ max(abs_tol, |reference| × rel_tol); counts are exact integers, and areas in square metres and distances in metres both use abs_tol = 1e-6, rel_tol = 1e-6. NaN/Inf are rejected. Geometry must have explicitly the same CRS: polygons use real Shapely area IoU (threshold 0.999999), non-polygons use topological equality or a Hausdorff distance ≤ 1e-6; two empty geometries are equivalent, one empty side is not; invalid geometry does not pass and is never repaired automatically; a missing or non-equivalent CRS does not pass. A bbox cannot replace real geometry.
- Ranking nDCG is only for future tasks that are explicitly supported and independently labelled; in this version rank must return `unsupported_rank` and must not pass for a supported task. Non-ranking tasks are not scored on ranking metrics.
- Preset acceptance: 160/160 contracts parse, no duplicate IDs/queries, 144/144 reference answers produced by real M04 allow-list calls and rebuildable byte for byte, 16/16 clarification/unsupported classifications correct; all scoring-boundary module tests pass, the full offline suite has at least 437 tests, and all historical audits pass. This is a gate for build/scoring correctness, not a system task success rate.

## Risks and boundaries

- Variants of a small public fixture are correlated and cannot be considered 160 independent geographic sources or open-domain generalization.
- M03 Phase 2 public queries are a catalog-informed internal evaluation. Fixed GTFS stop buffers are not real transit isochrones; this task set infers no real travel times.

## Supplementary freeze of the hidden split (before generating hidden content, 2026-10-07)

- The original 160 public dev v1 tasks stay where they are and are not overwritten. To meet the implementation plan's "add a hidden test set", the total task set is fixed at 200: public dev 160 + an independent private test of 40.
- The private test uses different synthetic coordinates and randomized Feature IDs, and stores inputs, tasks, the private seed and answers in the git-ignored `benchmarks/data/test/private/`. The public test directory publishes only a hash receipt without queries/answers/seed and the custody rules. Private content never enters development fixtures, prompts, knowledge aliases, logs or public reports.
- Distribution of the 40: 8 each for search, within_distance, nearest, within and spatial_join. The dedicated source data are still synthetic CC0 by the project author; answers are generated by actually executing the M04 allow-list. This internal hidden split is structurally related to the public M04b fixture; it can only show isolation from development queries and cannot be called independent external expert annotation. Formal test scoring must run after the model/prompt/configuration are locked; M11b only validates the data and scoring contract and does not run the M11c baselines.
