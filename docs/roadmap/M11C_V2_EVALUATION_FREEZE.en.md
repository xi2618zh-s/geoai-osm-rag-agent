# M11c v2 evaluation protocol freeze (m11c-protocol-v2, stage 1)

> **English translation.** The authoritative frozen document is the Chinese original [`M11C_V2_EVALUATION_FREEZE.md`](M11C_V2_EVALUATION_FREEZE.md). Its SHA-256 is recorded in the stage-2 freeze manifest and the frozen M11c v2 reports and is checked by code, so the original is kept byte for byte as evaluation evidence. This translation is provided for readers and is not part of the frozen evidence; if the two differ, the original applies.

- Date: 2026-10-07. This stage was published before private v2 was generated and before qwen touched any benchmark text. It freezes the number of tasks, distribution, independence, custody, model configuration, failure counting, gate and DONE rules. Stage 2 (prompt/code fingerprints) and stage 3 (dev result hashes and gate verdict) may only append; they must not change the rules in this file.
- v1 is unchanged: the m11c-protocol-v1 protocol, results (public dev strict 8/16/136, private v1 0/40), failure conclusion and receipt are all kept. The old private v1 has been used and can only serve as a "reused historical diagnostic set": after the v2 freeze it may be run once with the v2 formal configurations, reporting only aggregates labelled "reused, not evidence of generalization", and it must not be used for tuning, model selection or gate decisions.
- Approved by the user: options 3 + 4; questions written by a subagent and sealed after the user's review; the composition of the 48 tasks; the public dev entry gate.

## 1. Private v2 specification

- 48 tasks, 6 in each of 8 categories: search, buffer (single-dataset fixed-distance buffer, `task_type=within_distance`), nearest, within, spatial_join, aggregate_by_region, rank (unsupported), missing_place (clarification of a missing place/data scope). task_id `m11b_test_201`–`m11b_test_248`, `split=test`, `data_version=m11c-private-test-v2`; the task contract uses the M11b v2.0 fields and semantics (`src.evaluation.m11c.M11cPrivateTask`, which only relaxes the data version and ID range), and the scoring function `score_m11b` is unchanged.
- The structural semantics of the task families are the same as in M11b: search = filter one dataset by ≥1 attribute condition; buffer = fixed metre buffer of one dataset; nearest = filter source, then find its k nearest targets; within = filter source, then strictly within container; spatial_join = filter right, then join with left by intersects/within/contains; aggregate = filter values, then count/sum/mean/min/max over regions by a region key; conditions are FIELD eq/ne/gt/gte/lt/lte a number or string. rank expects error/`unsupported_rank`; missing_place expects clarification/`missing_place`, and its query names no catalogue dataset.
- Data: the question writer creates new project-synthetic CC0 GeoJSON (IDs or coordinates of old private/public fixtures must not be copied or merely transformed) with self-chosen dataset names and fields; `catalogue.json` declares each file's projected CRS; the last underscore-separated segment of the file name without extension is the role name and must be unique. Queries are written independently by the question writer: natural and varied, with complete parameters and no ambiguity, and may refer to datasets and fields by name or by natural paraphrase.
- Reference answers: `scripts/build_m11c_private_v2.py` reads the question writer's `task_specs.json`, actually executes the existing M04 AnalysisToolRegistry and generates expectations with the M11b v2.0 encoding (union geometry, count, `area_m2` when the union area > 0, `distance_m` as the minimum, explicit CRS, complete tool sequence). Automatic checks: 48 tasks with the 8×6 distribution, unique IDs/queries, 0 exact query overlap with public dev and private v1, files and hashes, valid CRS and projected CRS for buffer/nearest, existing fields, non-empty conditions, successful tool calls, contract validation, reference-prediction self-scoring 48/48, count of non-empty results (reported, not a failure criterion) and unique role names.

## 2. Custody and access

- The question writer is a fresh-context subagent that receives only this section's specification and the M04/M11b contracts; it must not read the public dev tasks, the M11b build scripts, the M11c front end/prompt/tests or private v1. The private package is stored in a separate workspace outside the repository (its path is passed only through the environment variable `GEOAI_M11C_PRIVATE_V2_DIR` or a command argument; the code has no default absolute path). Under the same operating-system user this is procedural isolation, not technical access control, and must be disclosed as such.
- The user reviews and may modify; after every modification the build is rerun and references and SHA-256 recomputed. After the user confirms, `seal` exclusively writes the public `benchmarks/data/m11c/m11c_private_v2_receipt.json` (only counts, category distribution, check results and hashes, without names, wording or answers); after sealing nothing may be modified, and the runner refuses to run on any hash mismatch.
- The development agent (the M11c implementer) receives only counts, category distribution, check results and hashes. The formal private run is performed by the author/evaluator role; the development agent gets back only aggregate scores and error categories without question content. Private raw model responses, predictions and per-task records are stored only in the private workspace.

## 3. Model front end (frozen configuration)

- Model: qwen2.5:3b, Ollama 0.13.5, manifest digest `357c53fb659c5076de1d65ccb0b397446227b71a42be9d1603d46168015c9e4b`, model blob `sha256:5ee4f07cdb9beadbbb293e85803c569b01bd37ed059d2715faa7bb405f31caa6`, GGUF Q4_K_M, 3.1B. Endpoint `http://127.0.0.1:11434/api/generate`, `stream=false`, `format` is the frozen JSON Schema (semantic frame). `/api/tags` digests are checked before running, and any mismatch is refused.
- Decoding: temperature 0, seed 1107, num_ctx 4096, num_predict 256, num_thread 4, use_mmap true (this machine's committed memory is not enough to load without mmap), keep_alive 30m. CPU only.
- Division of work: the model outputs only a semantic frame (operation, dataset roles, conditions, k, predicate, aggregation metric/field and so on); deterministic code checks that roles/fields exist, applies the rank/buffer rejection rules, infers join keys and renders the M07 command, after which M07/M08 decide the plan and execution. The model must never generate spatial results.
- Prompt: developed only on public dev and may contain examples derived from public dev; stage 2 freezes the text and its SHA-256. Any later change to the prompt, code or configuration requires a new version.
- Unavailability or failure: if the model fails to load or the service is unavailable, stop and report; do not switch models automatically or fall back to the rule-based front end.

## 4. Shared front end, call failures and cost accounting

- Each run first performs a front-end round: in that run's seed order, each task is called once (one "logical call"), and the resulting decision is shared by all configurations in that run (the three formal configurations and, on dev, FW-B, A2 and A3); A1 turns the front end off and does not call the model. For each prediction, `latency_ms` = that configuration's system time + that task's front-end time; `llm_calls` = the number of HTTP attempts of that task's front end (identical across configurations; the total number of unique calls is reported separately).
- Timeout: 120 s per HTTP attempt. Retries: at most 2 attempts per logical call; retry once only on timeout, connection/HTTP error, non-JSON or schema-invalid output.
- Model-call failure: the denominator is the number of logical calls in the run (160 per public dev run); the numerator is logical calls that still have no schema-valid frame after 2 attempts. A successful retry is not a failure but counts toward attempts; timeouts are counted among failure reasons. A valid frame with wrong semantics is not a call failure and shows up in scoring. Failed logical calls enter the systems as `unsupported/model_frontend_failed`. Reports include attempts, logical calls, failures, retries, timeouts, prompt/generation tokens and load and total times.
- Cost: local CPU, no API fees, `estimated_cost_usd=0`; model wall-clock time and token counts are reported separately, without converting to electricity cost.

## 5. Run order and gate

1. Freeze this file → subagent generates private v2 → user reviews/modifies → seal (public receipt).
2. Develop the prompt and adapter code on public dev → stage-2 freeze manifest (model digest, prompt SHA-256, decoding configuration, source fingerprint, SHA-256 of this file, SHA-256 of the private v2 receipt).
3. Formal public dev: the seven configurations (three formal + FW-B, A1, A2, A3) 3 times each, seeds 11071/11072/11073; write an exclusive dev report and result hashes (stage 3). The gate is checked for each of the three runs and passes only if all of them meet it: validator_replan strict ≥ 120/160; all 8 rank tasks `unsupported_rank`; ≥ 7 of the 8 missing-place tasks clarification/`missing_place`; model-call failures ≤ 2% (≤ 3/160 per run). If any run fails, stop and report: do not run private v2, do not switch models and do not fall back to the rule-based front end. 120/160 is only the entry gate, not a performance-improvement conclusion.
4. After the gate passes, the author/evaluator role runs one formal evaluation on private v2: the three formal configurations 3 times each (FW-B is not run on private); optionally, one diagnostic run on private v1 labelled "reused". The formal private evaluation is done only once; afterwards, the gate, prompt, code or questions must not be adjusted based on its results while still calling it a blind test.

## 6. Metrics, reporting and DONE

- Primary metric: the original M11b v2.0 strict pass. The secondary metric "strict pass excluding required_steps" is diagnostic only. Also reported: per-component pass rates, coverage, full/three-way common executable/two-agent/decision subsets, latency, tool and LLM calls, tokens, stability and error categories without question content, with explicit denominators. Buffer stays in the formal denominator and is unsupported; rank is unsupported.
- The report must list the per-configuration and per-task-category changes of v2 relative to v1 (public dev validator 136/160 and so on); private v2 is reported only in aggregate (including per-category aggregates).
- The DONE rule is unchanged: the three-way common executable subset of private v2 is non-empty, and all other conditions listed in the v1 protocol (3 runs each, ablations, stability, error analysis, fingerprints, exclusive reports, audits and tests) are met. If it is zero again, the failure result is kept and the blocking reason reported, and the test set is not replaced again.
- Re-checks: the M11c v1 receipt, the M11b and M07–M10 audits, the full offline test suite (at least the current 492 tests) and protected file hashes; v2 additionally provides a deterministic audit that replays the recorded raw model responses.
