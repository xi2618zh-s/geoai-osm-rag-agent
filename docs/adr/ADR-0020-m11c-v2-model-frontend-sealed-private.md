# ADR-0020: M11c v2 local model front end and an independently sealed private v2

- Status: Accepted (on 2026-10-07 the user chose options 3 + 4 and approved the composition of the 48 tasks and the public dev entry gate)
- Date: 2026-10-07
- Decision owner/Session: the user; M11c session (Claude Code)
- Affected modules: M11c; the M07–M10 public contracts, the agent tool allow-list, the M11b v2.0 scoring functions and the m11c-protocol-v1 results are unchanged.

## Context

The rule-based front end of m11c-protocol-v1 was written from public dev phrasing, parsed none of the 40 private v1 tasks, and left an empty three-way common executable subset on the private split. The aggregate results of private v1 have been seen, so it can no longer serve as a blind test; and the developer cannot write a new test set that the developer cannot read.

## Decision

1. The new protocol m11c-protocol-v2 (`M11C_V2_EVALUATION_FREEZE.md`) is frozen in three stages: rules and configuration before the private set is generated and before the model touches the benchmark; prompt/code fingerprints before the formal dev run; dev result hashes and the gate conclusion before the private evaluation.
2. The three formal configurations share a local qwen2.5:3b front end (digest, decoding, timeout and retries frozen). The model outputs only a semantic frame; deterministic code handles grounding and rejection rules, and M07/M08 handle planning and execution. Each run calls the model once per task, the decision is shared by all configurations within that run, and latency and calls are attributed to every configuration. If the model is unavailable or the gate is not passed, the evaluation stops; there is no automatic switch to another model or fallback to the rule-based front end.
3. Private v2 is written by a fresh-context subagent from a structural specification, with new synthetic data and independent wording; references are generated by real M04 tools. After the user's review it is sealed, and the public receipt contains only counts, distributions, checks and hashes. The private package lives in a workspace outside the repository; the formal private run is performed by the author/evaluator role, and the development agent receives only aggregates and content-free error categories.
4. The task contract keeps the M11b v2.0 fields and scoring (M11cPrivateTask only relaxes the data version to `m11c-private-test-v2` and IDs to `m11b_test_2xx`); the published M11b data, scorer and audits are unchanged.

## Alternatives

- Keep the rule-based front end and just widen its phrasing: still written by a developer who reads the public phrasing, and private v1 has already been used, so the evidence would be weak; not chosen by the user.
- Have the developer write private v2: cannot be kept invisible to the development side. Rejected.
- Generate the test questions with the same qwen model: question writer and solver would share a source, with uncontrollable bias. Rejected.
- Call the model separately for each configuration: model non-determinism would be confounded with architectural differences and CPU time would multiply; instead one front-end result is shared per run.

## Consequences

- Positive: the test questions are isolated from the development side; the comparison isolates architectural differences; cost and calls are auditable.
- Cost/risk: under the same operating-system user, isolation can only be procedural; the question-writing subagent and the development agent belong to the same model family; the 3B local model runs on CPU only and committed memory is tight (`use_mmap` is required); the 120/160 gate is only an entry condition.
- Testing and observability: private-builder and contract tests, offline model front-end tests (with mocked responses), replay audits, and re-checks of v1 and all historical audits.

## Migration and rollback

Everything new is an additive version; the v1 results, private v1 and M11b publications stay as they are. If the gate is not passed or the private common subset is empty, the v2 failure record is kept, without overwriting it or replacing the test set.

## Results (added 2026-10-07)

- After the stage-2 freeze, the public dev gate passed in all three runs; the single formal private v2 evaluation gave strict FW-A 6/48, dynamic 12/48, validator 34/48, with a three-way common executable subset of 5 (non-empty). Under the unchanged DONE criterion, M11c is DONE. See `benchmarks/results/m11c_v2/M11C_V2_FINAL_REPORT.md` and `docs/roadmap/M11C_V2_STAGE2_FREEZE.md`.
